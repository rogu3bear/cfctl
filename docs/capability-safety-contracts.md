# cfctl per-capability safety contracts

> Authority: this file records **why each governed capability is exposed the way
> it is** — the exact upstream shapes, readbacks, permission lanes, and
> compensation each one depends on. It is a companion to
> [docs/v2-security.md](v2-security.md), which owns the cross-cutting invariants
> (secrets, redaction, hashing, journal, evidence), and to
> [docs/runtime-policy.md](runtime-policy.md), which owns classification and
> approval.
>
> These entries constrain the capability they name. They are not additional
> cross-cutting guarantees, and a capability's absence here is not permission —
> the catalog and command surface decide whether it exists at all.
>
> Split out of `docs/v2-security.md`, which had grown to 41KB across 70 lines
> with single entries exceeding 900 words. Three load-bearing claims in it were
> found false in one review, and the volume was why. A security contract nobody
> can hold in their head is not serving as one.

- Account- and zone-scoped Access service-token updates are separately allowlisted by exact operation, path, product, selector, and permission. Both accept only `name` and `duration`; secret-version and prior-secret-expiration fields are rotation controls and fail request validation in this lane.
- Access service-token refresh is body-free, permission-bound, and irreversible. Apply and exact-resource readback must agree on the planned token identity and a valid future expiration; expiry values are never included in mismatch diagnostics.
- An exhausted approved MLNavigator D1 import is continued only by a separately approved `d1-resume-approved-mln-import-poll` PlanV2. Its closed caller input names the immutable parent plan and canonical exhaustion/accepted-ingest/bookmark hashes; cfctl derives the root migration, source, target, profile, current credential generation, catalog, input, and provider bookmark. Each child sends only bounded zero-retry poll requests. Sibling exclusion is keyed to the exact exhaustion, and any consumed or boundary-attempted child blocks reuse forever; only a cancelled pre-consumption draft may be replaced. Child exhaustion and completion stay in one cycle-free linear lineage joined back to the root import.
- Native token mint, value-roll, and revoke operations use live token-detail readbacks. Creation and rotation require the planned token to be active; revocation requires a not-found readback.
- Account- and user-owned token minting resolve every operator-selected permission-group ID against the matching fresh owner-specific inventory, normalize and hash-bind only auditable group metadata, and repeat that exact inventory check before durable plan consumption. User-owned minting requires explicit `--user --account <id>` input. Missing, duplicate, renamed, rescoped, wrong-owner, cross-account, or body/inventory-mismatched permissions fail before the mutation boundary. Generic token-create calls cannot bypass this workflow.
- Every minted policy binds an exact resource, never a wildcard or arbitrary input. Groups declaring account scope bind the one selected account; with `--zone <zone-id>`, groups declaring zone scope bind that one zone, and a single mint may carry both bindings. `--zone` is account-owned and rejected with `--user`. A group supporting neither scope fails the plan.
- Standing mint admission uses one fresh owner-specific permission response for two independent checks: the child plan's normalized selected subset must match its plan hash, and normalized metadata for the authority's complete approved allowlist must match its permission-inventory hash. Inventory reordering and unrelated additions remain valid; a missing or duplicated allowlisted group, or allowlisted name, scope, or category drift, fails closed. Standing token deletes do not require mint-inventory validation because they create no new token.
- Standing run admission uses OS-backed locks in the fixed order `plan -> authority`. Under the authority lock, cfctl reloads the grant, rechecks status and budget, durably reserves the run, and saves the authority before plan consumption. The durable reservation is the revocation linearization point: a revoke committed first blocks the run; an already-reserved run may finish. Plan consumption and the boundary-attempt checkpoint become durable before the authority lock is released for network activity, and later lineage writes reload and preserve `Revoked` rather than reactivating the grant.
- For a standing mint, a validated `BoundaryResponsePersisted` receipt bound to the same authority is token-lineage truth. After every secret-sink attempt, including failure, cfctl reconciles a successfully created token ID under the authority lock before verification. Later standing runs and `plans rectify` recover missing `minted_token_ids` entries idempotently from those receipts without replaying the Cloudflare mutation; malformed, unsuccessful, or authority-mismatched receipts add no lineage.
- Zone-scoped mutations whose only remaining gap is plan entitlement read the exact live zone subscription before planning. Only active official canonical tiers and explicit partner variants are evaluated against the OpenAPI plan matrix. The normalized receipt is hash-bound and re-read before durable consumption; inactive, unavailable, unfamiliar, or drifted plans fail before mutation. Account subscription lists are not accepted as zone-plan proof because they can contain multiple product-scoped subscriptions.
- Account-, global-, and user-scoped plan gates remain blocked when the official operation metadata supplies no exact product-scoped join from `x-cfPlanAvailability` to the account subscription inventory. cfctl names this unsupported resolution explicitly and never treats an arbitrary active subscription as entitlement proof.
- Every executable zone-scoped mutation reads the exact zone details before planning and execution, then requires the returned zone ID and `account.id` to match the selector and selected account. The normalized receipt is hash-bound; labels, local pins, cross-account targets, substituted responses, and ownership drift do not grant mutation authority.
- Token and DNS-record creation rectification may derive a separate revoke/delete plan only from the hash-bound returned resource ID. Compensation is never implicit: the new destructive plan requires its own review, approval, execution, and verification.
- Core DNS create, patch, replace, and delete mutations use exact record-detail readbacks. Create and update require the returned ID and every planned field to match both the apply response and live state; delete requires not-found. Mismatch evidence names fields but does not echo record values. Batch, import, scan, and review remain blocked until they have distinct safety contracts.
- Schema-derived exact-resource deletes are enabled only when the path ends in a resource selector, the DELETE has no request body or broadening controls, and the same product exposes a GET at the identical path. The optional string `cf-r2-jurisdiction` header is admitted only for R2 Bucket or R2 Object operations when both DELETE and GET declare it; the plan hash binds the selector and runtime repeats its planned value on the readback. The exact D1 database-detail GET may omit its optional `fields` projection only while the official selector contract states that omission returns every field. Optional GET conditionals are also omitted. Runtime rejects every other header, body, or query broadening before the mutation boundary and requires a live 404. Controlled reads and deletes remain blocked until they have an operation-specific mapping; deletion is recorded as irreversible without a prior snapshot.
- Selector-terminated PUT/PATCH operations receive a field-level same-path readback contract only when both operations are path-only or share the same R2 jurisdiction contract, the request schema is a non-empty object, and an official successful GET schema declares every writable field under `result`. The plan hash binds the read capability, path, canonical field allowlist, and any optional R2 jurisdiction selector. Runtime rejects every other header, query control, and unbound body field before mutation; readback repeats the planned jurisdiction and must recursively contain every planned field, while mismatch evidence names fields without values. Restoration remains unsupported until a pre-change snapshot is hash-bound.
- Turnstile widget creation is exposed only while the official collection route, inherited query shape, both accepted permission lanes, response envelope, and exact eight-field request schema remain unchanged. cfctl discards the collection's list-only query selectors, requires a new mode-0600 sink, redacts the returned secret from stdout and evidence, verifies the returned sitekey and every planned field through the exact detail read, and derives deletion only as a separate reviewed compensation plan. Updates use the same exact schema and field readback. Secret rotation pins the exact route, two-hour grace semantics, permissions, selectors, response, and one-boolean request schema; cfctl makes `invalidate_immediately` mandatory, requires a fresh sink, and records the operation as irreversible with no fictitious readback or rollback. All three have a zero direct incremental ceiling but remain subject to Free widget capacity and Enterprise account entitlements.
- Worker custom-domain attachment separately validates the raw `Workers Scripts Write` operation and an exact DNS-list companion that admits `DNS Read`, then exposes `Workers Scripts Write` plus `DNS Read` as the governed all-of permission set embedded in the plan. Planning and execution bind and repeat the active zone/account read, exact Worker settings read, exact-host custom-domain absence, and exact-host DNS absence. Missing DNS Read, companion drift, an inactive or cross-account zone, an absent Worker, or either hostname conflict blocks before attachment; DNS Write is not part of this lifecycle.
- Worker deployment normally requires the selected Wrangler config to equal an exact tracked `HEAD` blob. The sole private-config exception maps a root `wrangler.<role>.production.toml` to the adjacent tracked `wrangler.<role>.toml`, requires a mode-`0600` regular ignored file, and has a closed overlay: canonical lowercase D1 database-ID substitutions matched by exact binding; bounded canonical `send_email[].allowed_sender_addresses`; the two `disabled`/`enabled` split relay-mode variables; and `vars.MAILDESK_VERIFIED_SENDER_DOMAINS` only when the tracked template explicitly declares the empty string and the private file materializes a non-empty comma-separated list of at most 256 canonical lowercase DNS domains and 4,096 bytes. A repository-owned workspace-D1 operation additionally binds one exact selected D1 entry and may materialize a different canonical Worker name and selected `database_name`; that entry's canonical `database_id` and optional `preview_database_id` are admitted only when the preview equals the production ID. This operation-specific extension is selected by the planned database binding and is reused unchanged at launch; nonselected bindings and every other selected-entry field remain exact tracked authority. The domain list rejects wildcards, addresses, schemes, paths, ports, whitespace or controls, malformed labels, empty members, and duplicates after lowercase normalization. Normalization exists only for final parsed-document equality, so every other field remains exact tracked authority; plan and execution hash the actual private config and tracked template without retaining the private values. The plan labels authority explicitly as `exact_head_blob` or `private_d1_identity_overlay`; execution never infers the lane from a filename. Immediately before a private-config-bound Wrangler launch, cfctl opens the config and exact planned template with no-follow semantics, captures each bounded byte set once, and hashes and parses only those bytes. Both must match their planned identities before the private bytes are staged in an adjacent execution file and held until the complete child is reaped. Wrangler never receives the mutable source pathname. Raw stdout and stderr from that lane are never returned or persisted in any encoding; receipts and verification retain only canonical lowercase UUID version identities, deployment-match, message-match, owner-validated closed workspace-D1 row projections, categorical disposition, and the explicit fact that provider output was not retained. Parse and failure diagnostics are value-opaque. Generic delegated reads, tracked public configs, and configless service verification keep their ordinary output behavior. Workspace-D1 plans may still retain their separately governed selected database ID as operational target identity; that public plan field is not private subprocess output.
- Worker rollback is a dedicated native capability over the exact deployment-create route. The public input names only account, Worker, prior version UUID, expected current deployment UUID, and a bounded reason. Planning and execution read and hash-bind settings, retained deployment history, and exact version detail; the target must be prior, retained, inactive, and previously the sole version at 100 percent. The adapter fixes one version at 100 percent, shares one account/Worker lock with every local cfctl traffic mutation and GET-only rectification, adds a unique operation marker, never exposes or sends `force`, omits the undocumented idempotency header, attempts the POST exactly once, and verifies the returned deployment is the new latest deployment with the exact version and marker. Transport failures, HTTP 429, and HTTP 5xx rectify through a projected GET without replay; full deployment history is hash-bound but not persisted. Cloudflare exposes no conditional deployment write, so external deployment writers remain an explicit single-writer change-freeze prerequisite. Provider compatibility blockers remain terminal rather than triggering Cloudflare's force bypass.
- Repository-owned D1 migration authority accepts a preview-free production Worker binding or an inline preview identity equal to the production database, never a different preview database hidden in a deployable config. After a durable migration boundary response, `plans rectify` can repeat only the hash-bound ledger and labeled schema assertions; it cannot replay Wrangler apply, and it closes the plan only when both exact readbacks pass.
- Manifest-selected workspace D1 migration planning is fail-closed until two typed PostChangeVerification joins exist. `workspace-d1-qualification-produce` is the sole public producer: it consumes exact current PlanV2 identities, two distinct authenticated before/after OperationalProofV1 observations for every zero-delta claim, one authenticated exact-database not-found cleanup outcome, and one authenticated Founder-owned canary EvidenceV1 after their separately reviewed lifecycles. It performs no provider or Wrangler boundary, derives each zero-delta predicate from equal semantic state across receipts whose timestamps bracket the attempted operation, runs the closed validators, and returns the authenticated outer hashes plus six continuity joins. Identical observation identity, a successful database-detail cleanup response, or caller-authored canary hashes/disposition fail closed. `workspace_d1_provider_atomicity_v1` is the sole cfctl atomicity qualification: it binds one isolated database identity, the exact cfctl candidate and pinned Wrangler entrypoint, synthetic migration bytes, every child PlanV2, success plus DDL- and ledger-failure outcomes, independently observed zero schema/ledger deltas, credential/catalog scope, and confirmed database cleanup. `workspace_d1_old_worker_canary_v1` is a Founder-owned behavioral receipt under the explicit `mln-web.workspace-d1-old-worker-canary-v1` version-1 cross-repository contract: cfctl authenticates and validates the existing receipt, independently resolves every PlanV2 and operational-proof identity, requires the exact six-name evidence set, and checks self-hash, freshness, and PASS disposition while retaining only the Founder semantic-assertion SHA-256. cfctl does not author or re-sign the behavioral experiment. Founder—not generic Worker deployment—owns endpoint and business-row meaning. The PlanV2 join separately pins the existing Worker deployments, version-detail, settings, and Worker-deployment-plan evidence identities. Missing, malformed, stale, cross-candidate, cross-target, failed, or hash-drifted receipts cannot satisfy admission. Exact compiler-derived index and trigger definitions are compared by full SQLite schema equality; substring `schema_contains` is never exact migration proof. These contracts do not themselves unblock production.
- Repository-owned D1 evidence reads pin one clean committed declaration, fixed parameter-free query digest, production config and binding, and the exact body-free aggregate-plus-route-health column set. The unchanged `MaildeskD1EvidenceV1` aggregate is accompanied by an additive `MaildeskD1RouteHealthEvidenceV2` whose route and domain identities are hashed inside cfctl and whose types, count, completeness, timestamps, and error codes are closed and bounded. Caller SQL, PRAGMAs, parameters, partial route inventories, raw route IDs, addresses, domains, arbitrary rows, and private message fields are structurally absent from the public result. Provider rows are discarded after projection and both `provider_output_retained` and `body_returned` remain false; generic D1 query capabilities remain blocked.
- `r2-get-private-object-digest` is the only ordinary private-object read surface. It binds one normalized account/bucket/key target, streams at most 300 MB only into SHA-256 state, requires one ETag, and returns no bytes or output path. The generic raw `r2-get-object` adapter remains blocked, including when its OpenAPI operation is otherwise discoverable.
- Whole-host Access application updates and operator-group allow policy create/update are separate closed capabilities, not exceptions to the generic polymorphic APIs. They require exact ownership, complete prior snapshots for updates, terminal collection reads for ambiguity detection, exact-resource verification, and separately planned compensation or restoration. Unknown provider fields and union variants block before mutation.
- OAuth client creation is exposed only while the official collection route, account selector, raw OAuth Client Write permission, all-plan availability, closed request and response schemas, exact OAuth Client Read detail GET/delete companions, and response `/client_id` identity remain unchanged. The finalized governed lifecycle declares both `OAuth Client Write` and `OAuth Client Read`; resolver output, plans, preconditions, and verification retain that exact all-of set. The returned client ID selects exact readback of every planned non-secret field. Creation has zero direct incremental cost but is an approval-gated identity/ownership change; failed verification never authorizes automatic deletion. Every plan requires a fresh external operator-secret destination even for `token_endpoint_auth_method=none`. A returned secret produces only a mode-0600 `{client_id,client_secret}` JSON file; an omitted optional secret records `secret_returned:false` and creates no empty sink, while a missing secret for a secret-authenticated method requires rectification. The secret never enters stdout, plans, journals, or evidence; transaction receipts retain categorical sink status without copying the sink path.
- OAuth client update is exposed only while the official detail PATCH retains raw OAuth Client Write, the exact companion GET retains OAuth Client Read, all-plan availability, closed request/read schemas, and the all-field same-resource verifier remain unchanged. The finalized governed lifecycle requires both permissions. Planning snapshots and hashes the complete provider result while persisting only the bounded non-secret mutable projection and exact absent-field set; execution repeats the exact read and blocks on drift. Metadata restoration requires a separate snapshot-bound update. Visibility may change only as a one-field `private` to `public` promotion; it cannot be combined with metadata edits and is permanent because demotion is unsupported.
- OAuth client secret rotation and old-secret deletion are exposed only while the official rotate/delete route, operation IDs, account and client selectors, raw OAuth Client Write permission, exact OAuth Client Read detail companion, all-plan availability, body-free request, one-time `client_secret` response, delete identity response, and exact client-detail read remain unchanged. Both governed lifecycles declare the complete Write-plus-Read all-of set. Rotation requires a fresh mode-0600 sink and a hash-bound live precondition with `has_rotated_secret=false`; execution rechecks it before consumption, sinks and redacts the value, then proves the exact client reports `true`. Old-secret deletion is a separate destructive, irreversible plan that requires and rechecks `true`, binds the returned client identity, and proves the exact client reports `false`. A rehashed cross-account/client receipt, second rotation during overlap, deletion without overlap, stale state, missing sink, or grafted verifier fails closed. The delete is never represented as rollback because it destroys the old value and keeps the new one.
- D1 database PUT/PATCH is classified as a scoped reversible write only while its exact request contract contains the single `read_replication` field and retains the official `D1 Write` permission lane. Official pricing states that read replicas add no charge; ordinary row-read, row-write, and storage billing continues. The API accepts both `auto` and `disabled`, and the detail read verifies the planned mode, but cfctl still requires approval because no pre-change snapshot is bound for automatic restoration. Cloudflare notes that disabled replicas can take up to 24 hours to stop processing requests, so configuration readback does not claim immediate replica quiescence.
- Exact-resource deletes and updates may fall back to a parent-collection readback only when the mutation is path-only, deletes have no request body, updates expose a non-empty schema-proven field allowlist, the parent list exposes string item IDs, and pagination can be proven complete. Core contract validation repeats those shape rules, and runtime rejects query controls, delete bodies, and unbound update fields before mutation. The collection GET receives only its own safe pagination controls, never mutation inputs.
- Non-selector PUT/PATCH settings receive the same clean-GET field proof only when the official request schema is a non-empty object, the same product exposes GET at the identical path, and an official successful GET schema declares every writable field under `result`. Array/bulk bodies, partial response schemas, and cross-product path collisions remain blocked. No automatic restoration is claimed without a hash-bound pre-change snapshot.
- Generic create operations receive a lifecycle contract only when an official successful-response schema declares a string `result.id`, every planned request field is declared by the readback response, the POST is path-only, and the same product exposes exactly one path-only direct-child resource path with both GET and DELETE operations. The plan hash binds that path, identity selector, response pointer, read/delete capability IDs, and canonical field allowlist. Runtime rejects query controls and unbound body fields before mutation; verification reads the returned ID without forwarding the mutation conditional header. Rectification can only derive a separate delete plan from the hash-bound response receipt, and it refuses catalog IDs that no longer resolve to the exact bound DELETE path. Ambiguous paths, controlled operations, and undocumented response identities remain blocked.
- Git-integrated Pages production deployment is a dedicated bodyless create contract, not a generic-create exception. It is exposed only while the exact Pages Write POST, returned deployment ID, production-stage response fields, and exact deployment GET and DELETE companions retain their reviewed shapes. Verification polls the returned ID within a fixed bound and requires matching project identity, production environment, and terminal success. The operation has no direct API charge but can create downstream Pages build, Functions, and bandwidth usage. Traffic restoration is a separate reviewed Pages rollback; it cannot erase the deployment, reverse Functions side effects, or refund usage.
