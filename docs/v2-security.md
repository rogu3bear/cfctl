# cfctl v2 security contract

> Authority: this file is the security contract — it is authoritative for the
> **cross-cutting** invariants: credential storage, secret sinks, catalog and
> journal hashing, redaction, and evidence. What an individual governed
> capability depends on lives in
> [docs/capability-safety-contracts.md](capability-safety-contracts.md). For how
> the policy engine *classifies* a plan (`auto_execute` / `approval_required` /
> `blocked`), approval mechanics, standing authority, and the adapter boundary,
> `docs/runtime-policy.md` is authoritative. These documents restate several
> invariants in parallel by design; where they overlap they must agree — defer
> to runtime-policy on a classification or approval question, and to this file
> on a secret, journal, or redaction question.
>
> Every claim here constrains everything. If a claim is true only of one
> capability, it belongs in the companion, not here — that distinction is what
> keeps this document small enough to audit.

- OAuth uses Authorization Code with PKCE. Refresh tokens and imported keys are written to the platform keyring first — macOS Keychain or Linux Secret Service. When platform probing selects `fallback_file` because that keyring is unavailable (for example a login keychain desynchronized from the login password), cfctl fails down to a governed file store under its data directory (`auth/secrets`): a mode-0700 directory of atomically written mode-0600 files whose reads refuse any group- or world-readable secret. Once the governed fallback contains state, ordinary credential reads, locations, fresh writes, and logout deletion keep it authoritative without re-probing the platform keyring; only explicit repair or migration may inspect the keyring while fallback authority is active. `cfctl doctor` reports the active backend.
- The emergency global-key profile is never selected implicitly.
- Every governed login or credential import assigns a new random, non-secret credential-generation ID in profile metadata. Replacement first persists an unbound profile, writes the new secret, and then commits the new generation; a failure at either persistence boundary leaves proof-bearing reads blocked rather than reusing the old generation. Operational proof captures the committed generation before crossing the read boundary and freshness joins it to the currently installed profile generation, so replacing a credential cannot inherit prior permission or availability observations. Pre-generation profiles require login or import, and legacy proof without a generation remains readable but is never current.
- Secret-shaped request bodies are accepted only through stdin, stored temporarily in the platform secret store, and represented in plans by a hash and opaque reference.
- Secret-producing responses require `--value-out`; the destination must not exist and is created mode `0600` on Unix. Only a bare credential, a recognized secret field, or an exact two-field Access service-token or OAuth-client credential bundle is accepted. Account- and zone-scoped service-token creation are separate allowlisted operation/path/product/permission tuples; each bundle is created only when its required identity and secret fields are non-empty. OAuth client creation additionally requires an absolute destination under a pre-existing mode-0700 directory outside every Git repository. Receipts retain safe resource metadata while replacing secret values with `[SUNK]`.
- Per-capability safety contracts — the exact upstream route, schema, readback,
  permission lane, and compensation each governed capability depends on — are
  recorded in [docs/capability-safety-contracts.md](capability-safety-contracts.md).
  They constrain the capability they name; the invariants above are
  cross-cutting and constrain everything.
- Catalog-declared request header selectors are emitted only from the selected capability's selector object, which mutation plans hash-bind. Undeclared selector keys are ignored, required headers fail closed, invalid values are not echoed, and credential, host, idempotency, conditional, and hop-by-hop headers are reserved for governed runtime lanes rather than caller override.
- JSON request contracts recursively retain only bounded validation shape from local official-schema references: types, required fields, enums, nullability, formats, declared properties, array items, and additional-property rules. Descriptions, examples, and defaults do not enter executable plans. Before any network boundary, runtime validates nested objects and array items; an object with declared properties is closed to undeclared fields unless its pinned contract explicitly permits or schemas them. Recursive references and excessive depth stop contract expansion rather than importing an unbounded schema graph.
- Delegated subprocesses start with a cleared environment. cfctl restores only `PATH`, `HOME`, `NO_COLOR`, and the selected Cloudflare credential variables.
- Response-payload secret redaction is classification-dependent, not structural: it applies when the catalog classifies the operation as secret-sensitive, or when the operation is one of the exactly allowlisted credential operations (Access service-token creation, R2 temporary credentials, or OAuth client creation). The always-on structural layer is the narrower storage-boundary pass described below, which matches secret field names wherever they appear. A capability that produced secret material without carrying that classification would not be caught by the response pass.
- The storage-boundary redaction guard matches field *names*, so a document that legitimately carries those names as schema keys needs schema-aware handling rather than a blanket refusal. Access application and identity-provider create/update embed large request schemas whose properties include `client_secret`, `token`, `secret`, and `password` as configuration keys rather than secret values. Plan storage therefore redacts the pinned request schema through `redact_json_schema`, which resolves `$ref` and walks JSON-Schema name maps such as `properties` and `$defs`, and applies the generic fail-closed pass to every other plan field. A submitted `client_secret` is still refused as `SensitiveData`; a schema property of that name is not. Those capabilities are plannable where the catalog reports them governed — several of the update variants remain `blocked` for unrelated contract reasons. `docs/runbooks/cfctl.md` records the resulting contract.
- Evidence is redacted before it is content-addressed and written atomically. Qualifying descriptors and operational proofs are private storage-v2 envelopes authenticated with domain-separated HMAC-SHA-256 under a state-root-bound key held only in macOS Keychain or Linux Secret Service; this integrity key has no file fallback. Storage keeps capability-held handles for the evidence body, descriptor, and proof directories, rejects symlinked managed directories and entries, and verifies the complete public V1 payload plus the canonical state-root identity on every qualification load, hash, and list path. Equal redacted bodies deduplicate only under the same evidence class; a conflicting class fails closed. The public `EvidenceV1` and `OperationalProofV1` contracts remain unchanged. Historical body-only evidence remains readable through the explicit audit-body reader, while legacy unauthenticated descriptors and proofs are nonqualifying and are never silently upgraded. Workspace projections count those rows separately; only authenticated storage-v2 envelopes qualify, and malformed candidate envelopes are reported against their account without poisoning unrelated registered roots. `cfctl auth evidence-key init-preview|init|status|rotate|retire|adopt-preview|adopt-plan|adopt|recover-preview|recover-plan|recover` owns explicit lifecycle. Initialization spans the platform registry and the filesystem state-root marker, which no single transaction covers, so `init` publishes a private platform-held initialization intent naming the exact state root before the authority it names exists, and retires it only after exact marker readback. That ordering is the provenance boundary: a registry found without its marker is resumable only when the published intent names that exact registry, the registry is a fresh single-generation authority, and zero authenticated local artifacts exist. The intent carries no key material, and the state-root identity it holds is the same non-secret value the marker holds. An intent disagreeing with the registry fails closed. A registry with no intent is never resumable through initialization, so resumption cannot become a receipt-free path to inheriting an unattributable signing authority. Rollback of a fresh initialization retires its intent. A valid registry that is neither resumable nor adoptable is discarded rather than inherited: `reset` requires an absent marker, a fresh single-generation registry in direct platform custody, and zero authenticated descriptors and proofs, then removes that registry through the managed keyring teardown and initializes a new authority for a new state root. Reset is not adoption and is not weaker adoption. Adoption inherits an existing signing authority and therefore must authenticate the identity of the caller; reset inherits nothing, asserts no lineage, and yields exactly the state a clean host yields, so an installed-identity receipt would prove nothing about it. The zero-artifact precondition is what makes discarding safe, and it fails closed on a single authenticated candidate. Valid-registry adoption inspection is read-only: `adopt-preview`, `adopt-plan current`, and `adopt-plan status` preserve body-free classification and historical visibility without establishing executable authority. `adopt-plan create` and `adopt <plan-id> --yes` fail before plan persistence or marker crossing with `CFCTL_AUTH_INSTALLED_IDENTITY_RECEIPT_REQUIRED`. Raw caller-provided source, artifact, architecture, CDHash, algorithm, and provenance claims are not an authentication boundary. Signed publication and installation may proceed independently, but plan creation and execution remain unavailable until a separately reviewed producer and consumer can authenticate and bind the installed-identity receipt at the public manager boundary. Receipt-less historical plans remain readable but non-executable. A record-backed allocating pointer cannot publish or satisfy a crossing seal, project `marker_crossed`, complete, or re-enable evidence authentication; a matching marker without an exact active-plan seal remains a conflict. This release claims no adoption outcome. Malformed-registry preview is strictly read-only and classification-only: no raw value, digest, secret-derived identity, deterministic handle, private write, put, or delete is public or performed. A separate short-lived private platform-keyring intent binds the exact location, length, digest, classification, authenticated-artifact inventory, replacement authority, state root, timestamps, expiry, and lifecycle to a random opaque public plan ID. Confirmed recovery preserves exact original bytes in private quarantine before publishing the replacement, resumes the same plan forward after crossed transitions, finalizes a missing local marker, and is single-use or explicitly revocable before quarantine. Rotation retains old verification keys, retirement refuses an active or locally referenced generation, and quarantine retirement is separate. Presence of evidence is not proof that an operation was performed or verified.
- Plan execution gates on the evidence authority by reversibility, not by approval. `plans run` and its standing-authority lane both require a qualifying authority first and unconditionally, so a healthy installation proves the authority before it reads the plan record, resolves a credential, or reaches the provider. Only a non-qualifying authority consults the plan, and only to read its effect class. The decision consults both of a capability's classifications and either one is sufficient to force the refusal, because they genuinely disagree: `d1-import-database` is `DataWrite` by effect and `Irreversible` by risk, and thirteen mutating catalog capabilities share that shape, so reading `effect` alone would let a production database import proceed unattested. A `Destructive`, `ExternalCommunication`, `IdentityOrOwnership`, `Spend`, `Irreversible`, or `Unknown` effect keeps the refusal, as does a `Destructive`, `SecretSensitive`, `ExternalCommunication`, `IdentityOrOwnership`, `Spend`, `Irreversible`, or `Unknown` risk — disclosed material cannot be undisclosed, and an unclassified operation cannot demonstrate that it is replayable, so it fails closed. Only an operation replayable on both axes executes and reports `attestation.state=unattested_reversible_effect` with the reason the authority did not qualify. A plan that cannot be read keeps the refusal too, since an unreadable plan cannot demonstrate that its effect is reversible. This partition is deliberately not the planner's approval partition, which answers whether a human must approve. The attestation marker is telemetry, not a security control. It is written by the same installation whose evidence authority was unavailable, so it is unauthenticated and proves nothing against an adversary able to suppress evidence; it exists so that an honest failure is visible rather than silent, and it never substitutes for a qualifying evidence record. Every executed plan carries the marker because the execution path takes it as a required input rather than as a field a lane remembers to set. A degraded execution that crosses the boundary and then cannot write authenticated evidence is not a lost mutation: the existing post-boundary recovery lane marks the plan `RectificationRequired` and returns a typed envelope naming the durable boundary response, so a replayable effect performed without a receipt still ends in a state an operator can repair rather than in a bare error.
- Plans are one-use transactions. Their content, schema, account, targets, impact, policy, and approval are hash-bound.
- Mutation capabilities fail closed unless risk, effect, incremental cost, permissions, entitlement, operation-specific verification, and rollback or explicit irreversibility are known.
- Declaring an arbitrary verification or rollback string does not satisfy that contract. Strategy names must be implemented by the runtime and bound to the exact capability method, operation identity, and resource shape. Policy blocks unknown or grafted strategies, and the adapter repeats verification-strategy validation before the Cloudflare mutation boundary.
- Official product pricing indexes enrich catalog cost knowledge, but variable resource or usage pricing remains unbounded and therefore non-executable. An official pricing link is evidence, not a cost ceiling.
- Plans pin a hash of the executable capability catalog, including locally maintained adapter and safety contracts. The upstream OpenAPI hash is retained separately as source evidence. cfctl recomputes the executable hash before loading, saving, or indexing a snapshot; content drift blocks reads and planning. An explicit fresh `catalog sync` may replace an invalid current snapshot, but never promotes that invalid content over the last valid previous snapshot.
- Each transaction stage is appended to a hash-chained journal before or after its corresponding boundary: plan, approval, consumption, adapter attempt/response, secret sink, verification attempt/response, compensation, and close. Every checkpoint binds the plan status; apply, sink, and verification checkpoints also bind their redacted receipt hashes. Receipt drift, status drift, journal drift, or a missing predecessor blocks persistence and execution.
- A crash after durable consumption or an adapter-boundary attempt requires rectification; cfctl does not replay the mutation. Verification failure also enters rectification instead of being reported as success.
- Transport failures, governed-adapter handoff failures, input cleanup failures, and absent sink-only output receive explicit redacted response or sink checkpoints. They do not rely on an unjournaled status update to block replay.
- Local crash injection covers every transaction-stage transition by reopening the filesystem store and validating the last durable journal. Account-backed boundary interruption remains a separate smoke-test lane.
- The configured `CFCTL_HOME` is a trusted managed-state root. Plans and authorities use canonical lowercase UUID paths; traversal, absolute or malformed IDs, symlinks, non-regular files, and filename/document-ID mismatches fail closed. Evidence/proof authentication binds a random platform-held root identity to the canonical resolved state location and therefore fails closed when those authenticated artifacts are moved or grafted. This first keyed increment does **not** authenticate PlanV2, approval, standing-authority, or transaction-journal files: create-only authority creation and OS-backed guarded saves prevent cfctl concurrency from clobbering them, but coordinated same-user rewrites inside the trusted root remain outside their current integrity boundary. Extending the keyed design to those mutation-control records is a separate migration and authority decision; this contract is not a substitute for operating-system account integrity or a hardware-backed signature against a privileged local attacker.
- Telemetry is off. Local receipts leave the machine only through an explicit operator action such as attaching one to a pull request.

Report a suspected secret leak by preserving the operation ID and redacted receipt path, revoking the affected credential, and avoiding copies of the raw value in issues or chat.
