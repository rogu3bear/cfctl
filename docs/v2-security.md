# cfctl v2 security contract

- OAuth uses Authorization Code with PKCE. Refresh tokens and imported keys live only in the macOS Keychain or Linux Secret Service.
- The emergency global-key profile is never selected implicitly.
- Secret-shaped request bodies are accepted only through stdin, stored temporarily in the platform secret store, and represented in plans by a hash and opaque reference.
- Secret-producing responses require `--value-out`; the destination must not exist and is created mode `0600` on Unix. Only a bare credential or a recognized secret field is accepted. Receipts retain safe resource metadata while replacing the value with `[SUNK]`.
- Catalog-declared request header selectors are emitted only from the selected capability's selector object, which mutation plans hash-bind. Undeclared selector keys are ignored, required headers fail closed, invalid values are not echoed, and credential, host, idempotency, conditional, and hop-by-hop headers are reserved for governed runtime lanes rather than caller override.
- JSON request contracts recursively retain only bounded validation shape from local official-schema references: types, required fields, enums, nullability, formats, declared properties, array items, and additional-property rules. Descriptions, examples, and defaults do not enter executable plans. Before any network boundary, runtime validates nested objects and array items; an object with declared properties is closed to undeclared fields unless its pinned contract explicitly permits or schemas them. Recursive references and excessive depth stop contract expansion rather than importing an unbounded schema graph.
- Delegated subprocesses start with a cleared environment. cfctl restores only `PATH`, `HOME`, `NO_COLOR`, and the selected Cloudflare credential variables.
- Evidence is redacted before it is content-addressed and written atomically. Presence of evidence is not proof that an operation was performed or verified.
- Plans are one-use transactions. Their content, schema, account, targets, impact, policy, and approval are hash-bound.
- Mutation capabilities fail closed unless risk, effect, incremental cost, permissions, entitlement, operation-specific verification, and rollback or explicit irreversibility are known.
- Declaring an arbitrary verification or rollback string does not satisfy that contract. Strategy names must be implemented by the runtime and bound to the exact capability method, operation identity, and resource shape. Policy blocks unknown or grafted strategies, and the adapter repeats verification-strategy validation before the Cloudflare mutation boundary.
- Official product pricing indexes enrich catalog cost knowledge, but variable resource or usage pricing remains unbounded and therefore non-executable. An official pricing link is evidence, not a cost ceiling.
- Plans pin a hash of the executable capability catalog, including locally maintained adapter and safety contracts. The upstream OpenAPI hash is retained separately as source evidence. cfctl recomputes the executable hash before loading, saving, or indexing a snapshot; content drift blocks reads and planning. An explicit fresh `catalog sync` may replace an invalid current snapshot, but never promotes that invalid content over the last valid previous snapshot.
- Each transaction stage is appended to a hash-chained journal before or after its corresponding boundary: plan, approval, consumption, adapter attempt/response, secret sink, verification attempt/response, compensation, and close. Every checkpoint binds the plan status; apply, sink, and verification checkpoints also bind their redacted receipt hashes. Receipt drift, status drift, journal drift, or a missing predecessor blocks persistence and execution.
- A crash after durable consumption or an adapter-boundary attempt requires rectification; cfctl does not replay the mutation. Verification failure also enters rectification instead of being reported as success.
- Transport failures, governed-adapter handoff failures, input cleanup failures, and absent sink-only output receive explicit redacted response or sink checkpoints. They do not rely on an unjournaled status update to block replay.
- Local crash injection covers every transaction-stage transition by reopening the filesystem store and validating the last durable journal. Account-backed boundary interruption remains a separate smoke-test lane.
- Native token mint, value-roll, and revoke operations use live token-detail readbacks. Creation and rotation require the planned token to be active; revocation requires a not-found readback.
- Account-token minting resolves every operator-selected permission-group ID against a fresh account-bound inventory, normalizes and hash-binds only auditable group metadata, and repeats the inventory check before durable plan consumption. Missing, duplicate, renamed, rescoped, cross-account, or body/inventory-mismatched permissions fail before the mutation boundary. Generic token-create calls cannot bypass this workflow, and user-token minting remains blocked pending an equivalent contract.
- Zone-scoped mutations whose only remaining gap is plan entitlement read the exact live zone subscription before planning. Only active official canonical tiers and explicit partner variants are evaluated against the OpenAPI plan matrix. The normalized receipt is hash-bound and re-read before durable consumption; inactive, unavailable, unfamiliar, or drifted plans fail before mutation. Account subscription lists are not accepted as zone-plan proof because they can contain multiple product-scoped subscriptions.
- Account-, global-, and user-scoped plan gates remain blocked when the official operation metadata supplies no exact product-scoped join from `x-cfPlanAvailability` to the account subscription inventory. cfctl names this unsupported resolution explicitly and never treats an arbitrary active subscription as entitlement proof.
- Every executable zone-scoped mutation reads the exact zone details before planning and execution, then requires the returned zone ID and `account.id` to match the selector and selected account. The normalized receipt is hash-bound; labels, local pins, cross-account targets, substituted responses, and ownership drift do not grant mutation authority.
- Token and DNS-record creation rectification may derive a separate revoke/delete plan only from the hash-bound returned resource ID. Compensation is never implicit: the new destructive plan requires its own review, approval, execution, and verification.
- Core DNS create, patch, replace, and delete mutations use exact record-detail readbacks. Create and update require the returned ID and every planned field to match both the apply response and live state; delete requires not-found. Mismatch evidence names fields but does not echo record values. Batch, import, scan, and review remain blocked until they have distinct safety contracts.
- Schema-derived exact-resource deletes are enabled only when the path ends in a resource selector, the DELETE has no request body or broadening controls, and the same product exposes a GET at the identical path. The optional string `cf-r2-jurisdiction` header is admitted only for R2 Bucket or R2 Object operations when both DELETE and GET declare it; the plan hash binds the selector and runtime repeats its planned value on the readback. The exact D1 database-detail GET may omit its optional `fields` projection only while the official selector contract states that omission returns every field. Optional GET conditionals are also omitted. Runtime rejects every other header, body, or query broadening before the mutation boundary and requires a live 404. Controlled reads and deletes remain blocked until they have an operation-specific mapping; deletion is recorded as irreversible without a prior snapshot.
- Selector-terminated PUT/PATCH operations receive a field-level same-path readback contract only when both operations are path-only or share the same R2 jurisdiction contract, the request schema is a non-empty object, and an official successful GET schema declares every writable field under `result`. The plan hash binds the read capability, path, canonical field allowlist, and any optional R2 jurisdiction selector. Runtime rejects every other header, query control, and unbound body field before mutation; readback repeats the planned jurisdiction and must recursively contain every planned field, while mismatch evidence names fields without values. Restoration remains unsupported until a pre-change snapshot is hash-bound.
- Turnstile widget creation is exposed only while the official collection route, inherited query shape, both accepted permission lanes, response envelope, and exact eight-field request schema remain unchanged. cfctl discards the collection's list-only query selectors, requires a new mode-0600 sink, redacts the returned secret from stdout and evidence, verifies the returned sitekey and every planned field through the exact detail read, and derives deletion only as a separate reviewed compensation plan. Updates use the same exact schema and field readback. Both have a zero direct incremental ceiling but remain subject to Free widget capacity and Enterprise account entitlements. Secret rotation stays blocked until its irreversible or two-hour dual-secret cutover has a dedicated contract.
- D1 database PUT/PATCH is classified as a scoped reversible write only while its exact request contract contains the single `read_replication` field and retains the official `D1 Write` permission lane. Official pricing states that read replicas add no charge; ordinary row-read, row-write, and storage billing continues. The API accepts both `auto` and `disabled`, and the detail read verifies the planned mode, but cfctl still requires approval because no pre-change snapshot is bound for automatic restoration. Cloudflare notes that disabled replicas can take up to 24 hours to stop processing requests, so configuration readback does not claim immediate replica quiescence.
- Exact-resource deletes and updates may fall back to a parent-collection readback only when the mutation is path-only, deletes have no request body, updates expose a non-empty schema-proven field allowlist, the parent list exposes string item IDs, and pagination can be proven complete. Core contract validation repeats those shape rules, and runtime rejects query controls, delete bodies, and unbound update fields before mutation. The collection GET receives only its own safe pagination controls, never mutation inputs.
- Non-selector PUT/PATCH settings receive the same clean-GET field proof only when the official request schema is a non-empty object, the same product exposes GET at the identical path, and an official successful GET schema declares every writable field under `result`. Array/bulk bodies, partial response schemas, and cross-product path collisions remain blocked. No automatic restoration is claimed without a hash-bound pre-change snapshot.
- Generic create operations receive a lifecycle contract only when an official successful-response schema declares a string `result.id`, every planned request field is declared by the readback response, the POST is path-only, and the same product exposes exactly one path-only direct-child resource path with both GET and DELETE operations. The plan hash binds that path, identity selector, response pointer, read/delete capability IDs, and canonical field allowlist. Runtime rejects query controls and unbound body fields before mutation; verification reads the returned ID without forwarding the mutation conditional header. Rectification can only derive a separate delete plan from the hash-bound response receipt, and it refuses catalog IDs that no longer resolve to the exact bound DELETE path. Ambiguous paths, controlled operations, and undocumented response identities remain blocked.
- The journal detects local file drift and inconsistent stage transitions. It is not a substitute for operating-system account integrity or a hardware-backed signature against a privileged local attacker.
- Telemetry is off. Local receipts leave the machine only through an explicit operator action such as attaching one to a pull request.

Report a suspected secret leak by preserving the operation ID and redacted receipt path, revoking the affected credential, and avoiding copies of the raw value in issues or chat.
